# 0.2.1 재촬영·추가 검출 개선

## 범위와 데이터

0.2.0 배포 소스를 별도 `codex/release-0.2.1` 작업트리에 복사하고 1,579개 소스 파일의
SHA-256을 대조했다. 기존 작업 폴더와 0.2.0 배포물을 수정하지 않는다.
제품은 0.2.1, Flutter 내부 build는 24다. 모델 가중치와 Catalog payload는 유지한다.

확정 로그 132장·GT 1,096개를 전부 사용한다. 모델 가중치 학습에는 사용하지 않았지만,
0.2.0과 이번 개발에서 검출 정책 선택에 사용한 노출된 개발 세트다. 독립 일반화 검증이 아니다.
원본 이미지 SHA-256, 확정 category·visible bbox와 클래스 무관 IoU ≥0.5 최대 개수 일대일
대응을 유지한다. ERROR·IMAGE_RECAPTURE·미검출 객체도 분모에서 제외하지 않는다.

## 38개 영역 원인 분석

`scripts/diagnose_recapture_021.py`가 실제 decode·검출·분류·상태 판정을 실행하고,
HTTP 경로 외부의 진단 전용 hook으로 검출 점수와 분류 batch를 보존한다.
원본/GT/예측 비교에서 28장에 재촬영 38개가 있으며 실제 GT 9개·추가 박스 29개다.
추가 박스에는 빵의 일부, 샌드위치 속재료, 접시 가장자리 및 여러 객체를 감싼 영역이 있다.
GT 미대응이라는 표현은 사진에 픽셀이 없다는 뜻이 아니다.

실제 GT의 원인은 낮은 검출 점수 4개(81/84/122/123), 다중 객체 head 거부 4개(44/86/91/119),
경계 접촉 저신뢰 1개(41)다. 다중 객체 거부에는 이웃 객체에 가려진 정상 객체도 포함된다.
재촬영 원인이 겹칠 수 있으므로 원인별 합을 영역 총수로 해석하지 않는다.

낮은 점수의 조각 박스는 추가 재촬영을 만들고, 분류기의 이웃 소유권 마스크에도 참여한다.
초기에는 분류 전에 정리해 crop 마스킹도 줄이는 방법을 검토했지만, 남은 객체의 판정이 바뀌는
회귀가 확인되어 최종안에서는 이웃 context를 그대로 보존했다.
최종 상태를 재명명하거나 GT 객체를 지워 지표를 개선하지 않는다.

## 첫 후보의 기각과 context 보존 수정

첫 후보 `score040`은 로그와 원본 개발 조건을 통과했지만 후보 고정 뒤 고정300장 회귀에서
오승인 4→5건이 발생했다. CPU 정답 승인 1,356→1,357, 미검출 0→0이었지만 오승인 증가를
허용하지 않아 이 구성을 기각했다. CUDA에서도 같은 정확도 회귀가 재현됐다.
이 결과를 숨기거나 이전 freeze를 삭제하지 않는다.

원인은 로그 분석 때부터 확인한 출력 후보와 이웃 소유권 context의 결합이다. 첫 후보가
context도 제거해 남아 있는 ROI의 판정까지 바꿀 수 있었다. 수정은 특정 이미지나 class,
실패 객체의 좌표·점수에 대한 예외 없이 적용하는 context 보존이다. 가중치를 재학습하거나
고정300장의 GT에 맞춰 임계값을 조정하지 않는다. 새 수정의 회귀 기준은 유지된 모든 박스의
상태·reason·품목 순위가 baseline과 같아야 한다는 더 강한 불변 조건이다.

최종 후보 `context040`은 검출 context 점수 0.025를 복구하고,
`quality.detector_output_score_threshold=0.04`를 추가한다. 기존 전체 후보 목록은 이웃 마스크와
밀집도 분기에 보존하며, 출력할 ROI만 기존 `classify_selected`로 분류한다. 생략된 ROI는
내부 배치 위치만 유지하고 detail·verifier에서 다시 실행하지 않는다. 마지막 출력에서만
생략하고 segmentation ID는 연속 번호를 사용한다. 승인 점수 이상 후보를 숨길 수 없도록
출력 점수는 지역 재촬영 점수 0.25 이하로 검증한다. 새 필드가 없으면 이전 동작이다.

초기 HTTP 확인은 정답 승인 1,078, 오승인·미검출 0, 추가 검출 16, UNKNOWN 15,
재촬영 19개이며 남은 모든 ROI의 상태·품목·confidence가 baseline과 정확히 같았다.
CPU p50/p95/p99는 196.41/247.47/289.40ms다.

## 첫 후보의 개발 기록

기각한 첫 후보는 Runtime metadata의 `detector.score_threshold`만 0.025→0.04로 바꿨다.
D-FINE640 가중치, DINOv3 primary192/detail224, 선택적 ViT160, Catalog, 승인 임계값,
다중 객체 head, 경계 재촬영, 낮은 검출 점수 0.25의 지역 재촬영 판정은 유지한다.
검출 NMS와 전체 촬영 부적합 조기 종료, ERROR 응답도 유지한다.

로그의 제거된 21개 박스는 모두 기존 GT 미대응 박스다. 19개는 재촬영, 2개는 UNKNOWN이었다.
원본 302장·649개 객체는 정답 승인 646개, 오승인·미검출 0을 유지하고 추가 검출 16→5,
재촬영 15→4, UNKNOWN 4→4다. CPU HTTP p50/p95/p99는
123.99/190.94/219.03→108.03/185.51/197.12ms였다.

최종 수정도 반복 확인은 AB/BA/AB 순서로 CPU와 CUDA를 각각 측정한다. 각 쌍의 p95 증가를 숨기지 않으며,
한 쌍이라도 느리면 통과로 집계하지 않는다. 원본·로그 비교 후 후보를 고정하고 과거 고정300장은
회귀 확인에만 사용하며 그 결과로 재학습·임계값 변경을 하지 않는다.
실제 배포 EXE, checksum, 버전과 최종 테스트 결과는 배포 검증 보고서에 기록한다.

## N100과 남은 한계

N100은 ORT CPU detector(2 threads) → OpenVINO Intel UHD GPU primary/detail → 선택적 CPU
ViT verifier(4 threads) → CPU 후처리를 유지한다. GPU 초기화 실패 시 명시적인 CPU 시작,
GPU 실행 장애의 해당 요청 ERROR, CPU 재구성 후 다음 요청부터 CPU 사용, 재구성/실패 시
readiness 503 계약을 유지한다. provider fallback을 재촬영이나 성공으로 바꾸지 않는다.

N100 성능은 개발 완료 이후 대상 장비에서 측정한다. 개발 PC의 CPU/CUDA 수치는 N100 속도가
아니다. 현재 연결된 N100 대상이 없어 대상 장비 성능은 아직 확인하지 않았다.
로그에서 실제 GT 9개 재촬영과 추가 박스 10개 재촬영은 남는다. 낮은 점수의 실제 가림 객체와
조각 박스가 겹치므로 검출 임계값을 계속 올리면 실제 객체를 놓칠 수 있다.
더 넓은 환경의 촬영·새 실물·새 매장에 대한 일반화, SLA 또는 인증을 주장하지 않는다.

영역 이미지와 내부 trace는 명시적인 로컬 개발 진단 산출물이며 배포 Worker 기본 로그에
포함하지 않는다. 원본 데이터는 유지하고 진단 이미지는 검토 종료 후 해당
`artifacts/retraining/recapture-0.2.1` 폴더에서 삭제할 수 있다.
Checksum은 파일 손상·변경을 탐지하며 발행자 진위 인증을 제공하지 않는다.
