# 로그 기반 0.1.18 개선 기록

## 데이터와 판단 원칙

2026-09-09에 0.1.17 배포 소스에서 별도 작업 공간을 만들었다. 복사 후 일부 파일 내용이
0 byte 패턴으로 발견되어 원본과 byte 단위 대조·복구했다. 0.1.17 원본은 정상이며 변경하지 않았다.

확정 로그는 132장·1,096개 객체다. category와 visible bbox 사용자 확정 SHA-256을 확인한다.
SAM mask는 확정 범위에 없으며 이번 로그를 cutout이나 학습에 넣지 않는다. 원본 302장과
로그의 SHA-256 중복은 0개지만 같은 실물 컬렉션이다. 로그 전체를 하나의 관련 그룹으로 유지한다.
사진별 임의 train/validation 분할을 만들지 않는다. 로그 결과는 **학습 미사용 이미지 개발 비교**이며
독립 실물·매장 일반화 검증으로 표현하지 않는다.

기존 학습 원본 302장·649개 객체와 그 파생물만 학습에 허용한다. 학습 프로세스는 로그 폴더,
로그 검수 산출물, 과거 최종 benchmark 폴더 접근을 Python audit hook으로 차단한다. 이는
OS 수준 sandbox를 의미하지 않는다. 과거 최종 300장은 후보 선택 완료 이후 회귀 확인에만 사용한다.
이미 알려진 0.1.17 최종 실패 사례로 후보나 임계값을 설계하지 않는다.

## 측정 전 확정한 비교 기준

`configs/experiments/bread/log_improvement_018.json`에 데이터, 기존 EXE, CPU 프로필8/12,
warmup10, 3회 반복, 동시 요청1, IoU0.5 일대일 대응을 기록했다. 입력 파일 읽기는 HTTP 시간에서
제외한다. 시스템 오류와 재촬영, 누락은 정답 승인에서 제외한다.

기존 대비 오승인과 정답 승인이 악화되지 않고, 정답 승인11개 이상 증가 또는 오승인1개 이상
감소가 있어야 정확도 개선으로 채택한다. CPU p95는 기존 대비 5% 이상 느려지면 채택하지 않는다.
기존이 300ms 이내이면 후보도 300ms 이내여야 한다. 기존 원본의 정답 승인도 줄어들면 안 된다.
개선이 확인되지 않으면 기존 모델과 정책을 유지한다. 조건을 만족하려고 정답·분모·임계값을 바꾸지 않는다.

## 0.1.17 로그 진단

첫 반복에서 올바른 APPROVED 1,082/1,096개(98.72%), 오승인4개, 누락5개,
추가 검출9개, UNKNOWN8개, SEGMENT_RECAPTURE6개다. 완전 성공 이미지115/132다.
오분류 승인은0개이며 오승인4개는 GT와 대응하지 않는 추가 승인이다. 이미지83,123(2개),128이다.
GT 미대응은 사진에 실제 객체가 없다는 뜻이 아니며, partial/duplicate 박스도 포함한다.
로그에는 6개 장면29장, 8개28장, 9개52장, 10개23장이 있다. 기존 합성은 최대8개다.

품목 분류보다 검출의 위치·중복·밀집 장면 문제가 우선이라는 가설을 세운다. 승인 margin0.8,
선택 detail·Frozen ViT160·회전 검증과 ROI 다중 객체 recapture 정책은 유지한다.

## 후보 실험 순서

1. 기존 302장으로 학습된 D-FINE640 dense/basic 검출기만 baseline에 교체한다.
   분류기·Catalog·마스크 없는 입력·임계값·CPU8/12는 동일하게 유지한다. 기존 학습 소비 manifest를
   검증한 같은 원본 checkpoint만 사용하며 다른 빵 학습 모델을 가져오지 않는다.
2. 검출기 교체로 개선이 불충분하면 동일 원본의 실제 다중 장면을 더 많이 반영하는 검출기
   미세조정을 별도 설정에 먼저 고정하고 수행한다. 로그 bbox를 학습 label로 사용하지 않는다.
3. 실제 HTTP와 source 원본 회귀를 측정하고 최종 후보·코드·정책을 고정한 후 과거 최종300장을
   비교한다. 결과에 맞춰 재학습하지 않는다. CPU/CUDA, 빌드·버전·checksum·필수 테스트를 검증한다.

전체 결과는 `artifacts/retraining/three-bakery-improvement-0.1.18`에 보존한다.

## CPU 지연 실험 추가: 측정 전 확정

Baseline의 세 반복 p95는434.90/547.94/479.32ms다. classifier 단계 p95는413.30ms,
detector 단계는32.96ms다. 느린 요청에 UNKNOWN이 없는 경우도 있어 모델 경계 검증만으로
변동을 설명할 수 없다. Detector/primary/detail/ViT가 각각 가진 thread pool의 idle spinning
경합을 가설로 삼고, CPU session의 intra/inter-op spinning을 비활성화하는 단일 변경을 실험한다.
ONNX/Catalog/승인 정책과 CUDA는 동일하게 유지한다.

[ORT 공식 threading 문서](https://onnxruntime.ai/docs/performance/tune-performance/threading.html)는
기본 spinning이 CPU 자원을 사용하며 여러 session의 pool이 경합할 수 있다고 설명한다.
이는 현재 지연 원인이라는 확정이 아니라 실험 가설이다. `log_cpu_sleep_018.json`에 측정 전에
판정 결과·품목 순위 mismatch0, 정답 승인 감소0, 오승인 증가0, 매 반복 p95 20% 이상 감소를
채택 기준으로 고정했다. 속도만 개선되는 경우 모델·정책을 그대로 유지하고 검증된 실행 코드만 반영한다.

세 반복 로그는 상태·품목 순위396회 모두 같았고 p95는183.82/187.48/185.68ms였다.
원본302장도906회 모두 같고 정답645/649·오승인0을 유지했다. 원본 p95는약4~9% 감소다.
20% 개선 기준은 개선 대상인 로그 장면에 적용하고, 기존 원본에는 성능 회귀가 없는지 확인한다.

별도 Lite Worker PID25712가08:03:49에 시작한 사실을 발견했다. 초기 baseline 일부의 지연에
모델 로딩이 영향을 주었을 수 있으므로 그 속도 비교만으로 결론 내리지 않는다. 해당 앱을 종료하지 않고
CPU 소비를 기록하며 baseline/sleep을 AB,BA,AB 순서로 교차 측정한다. 다른 Worker의 CPU 소비가
측정 중0.5초를 초과하거나 프로세스가 바뀐 반복은 간섭 가능성이 있어 채택 증거로 쓰지 않는다.

## 확정 결과와 재현 순서

D-FINE dense/basic은 로그의 정답 승인이 각각 24/21개 감소했고 원본 정답도 1개 감소했다.
SSDLite 원본 재생 6epoch는 로그 정답이 2개 늘고 오승인이 1개 줄었지만 원본에서 새 오승인
1개가 생겨 기각했다. 원본 302장은 각각 96회 소비됐고 로그 이미지는 학습에 넣지 않았다.
`model-selection.json`은 기존 모델 유지, `release-selection.json`은 CPU 실행 변경만 선택한다.

CPU 교차 측정 3회 p95는 464.93→190.15, 468.55→193.38, 518.23→187.98ms다.
외부 Worker 시작·종료가 겹친 두 시도도 보존하고 채택 증거에서 제외했다. p50은 일부 반복에서
증가했으므로 모든 지연 지표가 개선됐다고 표현하지 않는다.

`scripts/prepare_release_018.py`와 `scripts/evaluate_release_018.py --freeze-only`로
선택·버전·Worker·Runtime·Catalog·정책·평가 코드 해시를 먼저 고정했다. 이후 전체 테스트와
`scripts/confirm_release_018_packaged.py`로 실제 0.1.17/0.1.18 EXE를 비교했다. 고정 300장의
정답 승인 1,352/1,410·오승인 4건은 같고 CPU p95는 약 44~48% 감소했다. 로그 배포 EXE
p95는 180.41/176.88/181.28ms, 상태·품목 순위 396회 일치다.

CUDA block 측정 중 한 반복에서 10.6% p95 증가가 관측되어 추가 회귀 진단의 AB,BA,AB 순서를
`scripts/confirm_release_018_cuda.py`에서 측정 전에 고정했다. 이는 추가 학습이나 모델 선택이
아니며 최초 결과를 보존한다. 최종 benchmark 접근 후 모델·정책·CPU 설정은 변경하지 않았다.

`scripts/report_release_018.py`는 측정 JSON에서 차이·결과·한계 문서를 만들고,
`scripts/verify_release_018.py`는 배포 8개 파일·ZIP CRC·구성요소 checksum·검증 증빙을 확인한다.
Lite 첫 빌드는 선행 installer manifest 생성 전 시작되어 실패했다. 완료된 manifest를 사용한
재실행은 성공했으며 실패·성공 로그를 모두 보존했다.
