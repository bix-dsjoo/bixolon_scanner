# 220장 Worker의 다음 진행 계획

기준: 2026-09-07. 이 문서는 다음 작업 순서이며 추가 학습이나 제품 배포의 실행 결과가 아니다.

## 기준 후보와 유지 조건

- 기준 후보: `artifacts/retraining/limited220-context`.
- 원본: 기존 단일 200장과 선정 멀티 20장. 다른 280장의 pixels는 사용하지 않는다.
- 현재 같은 실물 진단: 정답 승인 134/136, 오승인·검출 FN·Top-3 누락 0.
- 반복 실행 p95의 중앙값: CPU 349.9ms, CUDA 193.0ms. CUDA 개별 실행 p95는 100.1~238.4ms.
- 우선순위: 오승인 → 검출 누락·Top-3 누락 → 정답 승인율 → 지연.
- 승인 임계값 0.8과 전역 routing 계약을 유지한다. SKU·image ID별 우회를 추가하지 않는다.
- 실험 중 제품 버전은 0.1.15이며 활성 번들을 교체하지 않는다.

## 1. 측정 분산과 경로별 비용 확인

추가 학습 전에 현재 후보의 느린 구간부터 계측한다. 같은 실행 환경·provider·ONNX·Catalog를
고정하고 실제 사용 provider, CPU thread 설정, 다른 부하 유무를 함께 기록한다.

1. 실제 HTTP Worker 한 프로세스를 유지한 측정과 새 프로세스 시작 후 측정을 분리한다.
2. 시작·warmup 시간을 별도 기록하고 고정된 20장을 최소 5회 반복한다. 원본 20장과 요청
   100회를 구분한다. Detector 조기 종료와 full-path도 분리한다.
3. decode, Detector, ROI crop/mask/resize, primary, detail, verifier, 최종 판정의 시간 및
   각 경로의 ROI 수·batch 크기를 수집한다.
4. p50/p95/p99와 표본 수, 실행별 편차를 기록한다. 개선 전후를 교대로 측정한다.

산출물은 지연 분해 보고서와 가장 큰 병목 한 가지다. CUDA 지연 변동 원인을 확인하기 전에는
단발 최저값으로 속도 개선을 판단하지 않는다.

## 2. UNKNOWN 2개와 과도한 승인 위험 진단

image 299 / bread_09는 점수 0.304, image 126 / bread_07은 0.770이다. 둘 다 Top-1은 정답이고
bbox IoU는 각각 0.942와 0.964다. 큰 검출 위치 오류보다 가림과 분류 증거 부족을 우선 조사한다.

- 같은 객체의 GT ROI와 Detector ROI, 마스크 적용 전후, 192/224 입력을 비교한다.
- 어려운 두 사례뿐 아니라 정상 승인 객체에서도 같은 비교를 수행해 전체 영향을 확인한다.
- 원본 220장으로만 고정 seed의 가림·조도·crop 변화 진단 세트를 만든다. 학습 증강과 seed를
  구분하되 독립 validation이나 실제 미등록 객체 검증으로 부르지 않는다.
- 실제 보이는 정보가 부족한 사례의 UNKNOWN은 허용한다. 99%를 맞추기 위한 강제 승인을 하지 않는다.

산출물은 원인별 오류표와 다음 학습에서 바꿀 전역 증강 한 가지다.

## 3. 남은 두 학습 후보를 대조 실험으로 사용

현재 4개 후보를 실행했으므로 기존 최대 6개 계획 안에서 2개만 추가한다. 두 후보 모두 현재
context checkpoint에서 출발하고, seed·학습률·loss·고정 4 epoch·원본을 동일하게 둔다.

| 후보 | 변경 | 검증 목적 |
|---|---|---|
| 5: 대조군 | 현재 학습 recipe로 4 epoch 추가 | 추가 학습 시간만으로 생기는 효과 측정 |
| 6: 개선군 | 같은 4 epoch에 2단계에서 정한 전역 증강만 변경 | 증강 자체의 추가 효과 측정 |

개선군은 후보 5의 checkpoint에서 시작하지 않는다. Detector와 frozen verifier는 검증된 기존
산출물을 재사용하고 변경된 classifier의 primary/detail만 export한 뒤 Catalog를 다시 만든다.
마지막 epoch를 사용하며 같은 실물 진단으로 checkpoint나 threshold를 자동 선택하지 않는다.

정상 멀티 20장과 파생 스트레스 진단을 모두 비교한다. 오승인·검출 누락·Top-3 누락이 증가하면
승인율 상승만으로 개선이라고 판단하지 않는다. 개선이 없으면 기준 후보를 유지하고 원인을 기록한다.

## 4. 확인된 추론 병목 한 가지 최적화

1단계 결과를 바탕으로 중복 전처리 재사용, 실제 batch의 warmup 누락, 선택 경로의 불필요한
반복 실행 중 확인된 원인부터 수정한다. 원인 확인 없이 입력 해상도·정밀도·승인 정책을 동시에
바꾸지 않는다. 모델 변경과 실행 최적화의 비교 결과를 분리한다.

각 수정 후 상태·class rank parity, bbox IoU 및 승인 점수 오차를 검사한다. 현재 비교 기준은
bbox IoU 0.999 이상, 승인 점수 오차 0.005 이내이며 최종 상태·class rank는 같아야 한다.
지연 목표는 CPU p95 250ms, CUDA p95 70ms다. 미달하면 구간별 잔여 비용을 보고한다.

## 5. 장기 실행 복구와 최종 정리

현재 timeout 뒤 readiness 차단은 구현됐지만 영구 native hang의 강제 복구는 남아 있다.
추론을 별도 프로세스로 격리하고, deadline 초과 시 오류 응답·프로세스 종료·재기동·warmup·
readiness 복구가 순서대로 이루어지는 감독 구조를 설계·검증한다. 모델 장애는 계속 ERROR이며
재촬영으로 바꾸지 않는다. 이미지와 내부 경로는 기본 로그에 남기지 않는다.

실제 HTTP에서 정상 입력, 손상 입력, 연속 요청, timeout, 강제 hang과 복구, 반복 실행의 메모리
추이를 검사한다. 테스트에는 정해진 시간 제한과 종료 조건을 둔다. 최종 변경에는 전체 Python/
Flutter 테스트, Ruff, Flutter analyze, git diff 검사를 수행한다.

최종 산출물은 후보별 비교표, 최선의 관측 후보 Runtime/Catalog, 실패 사례, 반복 실행 명령과
미달 목표다. 모델 목표는 정답 승인 135/136 이상으로 두되 오승인 방지를 앞세운다. 최대 6개 후보
또는 2회 연속 개선 없음이면 같은 진단에 맞추는 반복을 멈추고 원인·데이터 한계를 재검토한다.

같은 실물만 있는 현재 220장으로 새 실물·미등록 객체의 오승인률을 검증할 수는 없다. 별도의
독립 평가 자료가 추후 허용되면 학습 220장과 분리해 평가 전용으로 사용한다. 이는 현재 계획의
추가 학습 원본을 늘리는 조건이 아니다.
